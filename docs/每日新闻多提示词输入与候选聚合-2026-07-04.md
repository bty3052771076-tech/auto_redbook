# 每日新闻多提示词输入与候选聚合（2026-07-04）

## 背景

GUI 的“自动发帖”页原先只有一个提示词大文本框。用户在生成“每日新闻”时经常需要同时覆盖多个方向，例如“世界杯 / 体育 / 足球”或“财经产业 / 公司政策 / 市场变化”。如果把这些内容塞进一个提示词，新闻源可能只按整句检索，导致三日窗口内没有候选，最终报错：

```text
no daily news candidates matching the prompt within the Beijing three-day window
```

本次修改目标：
- GUI 不再使用一个大框表示提示词，改为多个独立方向输入框。
- 每个框代表一个检索方向，自动发帖时合并为多行提示词传给 CLI。
- “每日新闻”候选获取会将提示词拆成多个查询变体，分别获取候选，再统一去重和筛选。
- 对空格分隔的提示词补充分词查询，例如 `世界杯 体育 足球` 会扩展为 `世界杯 体育 足球`、`世界杯`、`体育`、`足球` 和英文补充查询。

## GUI 行为

“自动发帖”页的提示词区域现在固定显示 4 个方向输入框：

```text
方向 1    [                    ]    方向 2    [                    ]
方向 3    [                    ]    方向 4    [                    ]
```

填写规则：
- 每个框填写一个检索方向。
- 空框会被忽略。
- 重复方向会被去重。
- GUI 自动运行环境变量 `AUTO_REDBOOK_GUI_PROMPT` 仍然兼容旧写法；程序会按换行、竖线或分号拆回多个方向框。

最终传给 CLI 的 `--prompt` 是多行文本，例如：

```text
世界杯
体育 足球
财经政策
市场变化
```

后端 `_split_news_queries()` 会把多行提示词拆成独立查询，避免把所有方向强行合并成一个过窄的检索词。

## 每日新闻候选获取逻辑

当 `prompt_hint` 不为空时，`fetch_daily_news_candidates()` 使用 `_build_prompt_news_queries()` 生成查询序列。

示例：

```text
输入：世界杯 体育 足球
查询变体：
1. 世界杯 体育 足球
2. 世界杯
3. 体育
4. 足球
5. world cup
6. sports
7. football
8. 默认新闻查询
```

外部新闻源会围绕这些查询变体获取候选。非默认查询的候选会聚合到同一个候选池中，经过：
- URL 和标题去重
- 历史已用 URL 去重
- 北京时间三日窗口过滤
- 提示词相关度过滤
- 热度、时效性和来源评分排序

这可以避免“第一个整句查询抓到了旧新闻，就不再尝试拆分关键词”的问题。

## 边界说明

- 三日窗口仍然严格使用北京时间生成日、生成日前一天、生成日前两天。
- 默认新闻查询只作为补充，不会优先覆盖用户明确输入的方向。
- `file` 和 `hotnews` 这类本地或榜单型来源保持原有入口，避免因为一次 GUI 输入改动改变它们的成本和行为。
- 本次 GUI 改动只改变提示词收集方式，不写入任何 API Key，也不改变 `.env.gui` 的存储规则。

# 异常重复草稿乱码与占位内容修复 - 2026-07-24

## 目标

修复小红书创作者中心草稿箱中出现的异常重复草稿：无语义乱码标题、相同旧图片反复出现，以及“生成失败，请稍后重试”仍被保存为草稿的问题。

## 问题复盘

本地 `data/posts/` 记录显示，异常草稿集中创建于北京时间 `2026-07-24 11:03` 至 `11:24`。问题由三项缺陷叠加造成：

1. 部分中文文本在终端或模型响应边界发生 UTF-8 被当作 GBK/GB18030 解码的错误，形成如“姣忔棩鏂伴椈”“璐㈢粡...”一类可逆乱码；上传器此前会原样保存。
2. 文案模型触发 `429 RATE_LIMIT_EXCEEDED` 后，生成层返回“生成失败，请稍后重试”的占位结果。普通生成流程没有识别该失败标记，仍将其视为普通草稿上传。
3. GUI 的 AI 生图模式使用 `assets/empty/*` 作为“不要本地素材、改为自动生图”的历史哨兵；该目录后来被放入两张旧截图，CLI 因而将其当成真实素材复制并反复上传，而没有调用生图模型。

同批中存在内容相同或高度相似的草稿，批量上传前也缺少最终重复拦截。

## 实施计划

1. 在 LLM 输出、CLI 输入和发布校验三处建立统一的文本完整性门禁。
2. 将限流从“生成失败后留下占位文案”调整为“有限重试，最终失败即中止”。
3. 固化自动生图哨兵的路径语义，并在批量上传前增加内容指纹去重。
4. 用离线测试覆盖异常输入、限流、图片选择、每日新闻兜底和 GUI/CLI 回归；测试不得读取本机真实新闻源凭据。
5. 不自动删除历史草稿，保留人工在创作者中心确认和删除的控制权。

## 修复设计

### 1. 文本完整性

新增 `src/text_integrity.py`：

- 仅在命中明确乱码特征且 `GB18030 -> UTF-8` 反向转换成功时修复文本。
- 最多修复两次，覆盖经过两次 Windows 代码页边界的内容；修复发生在标题长度截断之前，避免乱码字符被截断后无法还原。
- 正常中文不会触发转换。

该修复应用于 LLM 输出的标题、正文、话题和生图事件描述；CLI 对标题与提示词也会先进行修复并输出警告。

### 2. 失败内容不得上传

- 普通生成流程收到 `_fallback_error` 时直接失败，不再保存或上传占位草稿。
- `validate_post` 会拒绝可恢复乱码，以及“（生成失败，请稍后重试）”正文。
- 在本地对本次异常草稿执行只读 `validate`，已得到乱码和失败占位的拒绝结果。

每日新闻保留原有的基于新闻材料的离线事实兜底；它不会使用普通生成的失败占位内容。

### 3. 限流重试

`generate_draft` 遇到 `429`、`RATE_LIMIT` 或限流提示时，默认等待 `65` 秒后重试一次，避免 5 RPM 的模型在十条批量任务中后半段直接落入失败占位。

可通过环境变量 `LLM_RATE_LIMIT_RETRY_SECONDS` 调整等待时间。该变量仅控制等待时长，不包含任何密钥。

### 4. 生图素材边界

`assets/empty/*` 和 `assets/empty/**` 现被 CLI 明确定义为自动生图哨兵，即使目录中存在残留文件，也会传入空素材列表，从而执行配置的 AI 生图流程；AI 生图失败时仍沿用已有 Pexels 兜底策略。

本地图片仍应使用其他明确路径，例如 `assets/pics/*`。

### 5. 批量重复拦截

`auto` 命令在上传前基于标题和正文的规范化指纹去重。指纹重复的后续草稿会标记为失败并跳过上传，控制台会给出与首条的对应关系。只有已通过校验、即将进入上传链路的草稿才会登记指纹；先前校验失败的草稿不会误拦截后续有效替代稿。

## 历史草稿处置

本次修复不会自动删除创作者中心中的旧草稿，也不会修改已上传的历史内容。截图中的异常项可在创作者中心手动删除；删除它们不会影响此前已核验的十条每日新闻草稿。

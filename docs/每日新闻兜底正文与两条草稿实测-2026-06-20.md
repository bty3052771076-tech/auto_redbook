# 每日新闻兜底正文与两条草稿实测

## 背景

本次再次执行 2 条“每日新闻”生成与保存草稿测试时，首次实时链路未生成草稿：

```text
[daily_news] no successful posts (failed=0, skipped_quality=7)
创建完成：posts=0
error: no posts created
```

终端显示 LLM、新闻获取、图片配置都不是直接失败点。失败发生在每日新闻质量闸门：多个候选被判定为 `generic_body`，因此没有进入生图与上传阶段。

## 根因

当 LLM 返回的正文过泛时，流程会回退到 `_daily_news_offline_body()`。但旧的兜底正文模板在信息不足和信息可用两种场景下都使用同一套“保守泛化”句式，例如“现有信息仍有限”“根据原始来源提供的公开信息”等。

这些句式本来是为了避免无依据推测，但它们也被质量闸门视为泛化正文。因此出现了“兜底模板生成后又被质量闸门拦掉”的冲突。

## 修复

已在 `src/workflow/create_post.py` 增加基于候选上下文的兜底正文分支：

- 如果候选有可用标题、摘要或正文片段，会生成更具体的中文正文，并保留“不要推测”的保守表达。
- 如果候选信息确实稀疏，仍保留旧的泛化模板并继续被质量闸门拒绝，避免发布空泛内容。
- 英文候选仍输出中文正文，不把英文标题或 URL 塞进正文。

新增测试覆盖：

- 有明确标题/摘要的新闻候选，兜底正文不应触发 `generic_body`。
- 真正稀疏的候选仍会被质量闸门拒绝。
- 英文候选的中文兜底正文长度仍符合发布要求。

## 实测结果

为避免 NewsAPI/GDELT 实时限流或低质候选影响验证，本次成功链路使用本地已核验 API 候选缓存：

```powershell
$env:NEWS_PROVIDER="file"
$env:NEWS_CANDIDATES_FILE="data/news_candidates_api_cache_2026-06-20.json"
$env:IMAGE_PROVIDER="aliyun"
$env:ALIYUN_IMAGE_MODELS="wan2.7-image,wan2.7-image-pro"
$env:XHS_HEADLESS="1"
.\.venv\Scripts\python.exe -m apps.cli auto --title "每日新闻" --assets-glob "assets/empty/*" --count 2 --login-hold 600 --wait-timeout 600
```

生成并保存到小红书草稿箱的结果：
